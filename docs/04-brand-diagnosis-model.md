# 品牌诊断模型：从"温度计"到"体检报告"

> 项目卡片 · 2026.09（规格 v2.3）· 角色：产品定义 + 模型设计 + 验收口径 · 状态：MVP 已实现，外部数据源未接入；项目 2026.10 中止，发布前验收未走完

这篇文章讲诊断产品最容易走过的那条路：**给品牌打一个 0–100 分**。我选择不走，因为这个分数既解释不了原因，也指导不了行动——而"解释原因 + 给出下一步"才是诊断真正的价值。

---

## 1. 测量与诊断必须分开

在我这里，这是两个产品：

| | 品牌实测 | 品牌诊断 |
|---|---|---|
| 回答的问题 | **What**：品牌在 AI 答案里到底可不可见、被谁引用、趋势如何 | **Why / How**：为什么不可见、先改哪一项 |
| 比喻 | 温度计 | 体检报告 + 治疗方案 |
| 数据来源 | 向 AI 平台真实提问、采集回答与引用 | 已有合格实测 + 官网自查 + 全网信源清单 |
| 产出 | 提及 / 推荐 / 挂源等表象指标与趋势 | 三层客观结论 + ≤5 张优先行动卡 |

**为什么必须分开**：

- 测量是"客观记录"，诊断是"归因判断"。混在一起，用户会以为"分数低 = 有个总分要刷"，而不是"某一层供给有缺口"；
- 诊断如果自己再去采集一遍 AI 回答，会与测量口径不一致、重复占用采集资源，还容易把"采样的偶然"当成"诊断的结论"。

所以我的诊断**不向 AI 平台独立提问、不维护并行题集、不做独立采集**。它只做三件事：官网类根因自查、读最近一次合格实测做归因、拉全网信源清单。

> 这也是一个刻意的取舍：代价是诊断**依赖一次合格实测**，新用户冷启动时部分维度只能标"未评估"。我认为这比"诊断自己另测一遍、然后和实测数字对不上"更诚实。

---

## 2. 三条"诊断合法性条件"

这是我给诊断定的**充要条件**。三条同时满足，诊断才成立；缺一条，它就会变成"看起来专业的废话"。

### 条件一：量的是用户改得了的供给

- **含义**：诊断的每个判断，都必须对应一个用户能通过自己的动作改善的东西（官网能不能打开、AI 爬虫有没有被拦、页面结构是否可摘取、品牌事实是否一致……）。
- **反例**：把"AI 平台更偏好哪家媒体"、"行业平均被引率"当成诊断项。用户听完只能摊手。
- **设计落点**：只有"可干预供给项"才参与雷达投票；不可干预的事实项（比如工商登记信息是否一致）只作为**核对结果**呈现，不当作"努力分"。

### 条件二：不能把实测结果换名再报一遍

- **含义**：诊断页面里的每个结论，要么是实测没给的信息（归因），要么是实测数据的另一个视角；不能把"提及率 13%"改叫"采纳层得分 13 分"再报一次。
- **反例**：诊断页顶部直接放"提及率 / 推荐率"两个大数字——那用户不如直接去看实测页。
- **设计落点**：诊断页**不出现**提及率/推荐率头条；实测结论只以"证据"形式出现（问法原文 + 客观状态标签 + 可下钻的原回答），且不做 LLM 摘录，避免"来源不明的一句话"。

### 条件三："通过"不能靠"没测"制造

- **含义**：没有数据时必须说"未评估"，不能因为"没发现问题"就给一个通过。反过来也一样：**未评估不能画成失败**。
- **反例**：信任层数据源没接，雷达图上却显示"信任 0 分"——用户会以为自己的信任有问题，其实只是没测。
- **设计落点**：
  - 每个子项五种状态：通过 / 缺口 / 待核对 / 未评估 / 无问题可判；
  - 雷达只连接"有值"的层，没有可投票项的层**断开并标注"待核查"**，不落到中心画成 0；
  - 每轴标注"已核查 k / n"，让用户知道这个形状覆盖了多少项。

> 第三条尤其重要：它同时防两种自欺——**"没测 = 通过"（乐观造假）**与**"没测 = 0 分"（悲观误导）**。我在实现里真的踩过后者：雷达把未核查维度画成 0 分，页面右侧却写"当前没有缺口"，自相矛盾。修复方向是 null 断开 + 虚线问号，这条被写进发布前验收清单。

## 3. 三层归因：信源 / 信任 / 采纳

诊断对外只讲三层。每一层只回答一个问题，且只对"用户能改的东西"下判断。

| 层 | 回答的问题 | 证据来源 | 用户能改吗 | 输出 |
|---|---|---|---|---|
| **信源** | AI 有没有"读到"你 | 官网自查（可达、爬虫规则、可摘录结构）+ 全网信源清单 | 能（改官网、改 robots、改内容结构） | 客观结论 + 缺口卡 |
| **信任** | AI 敢不敢"用"你 | 主体事实核对（工商/资质/公开风险记录）+ 实测中的口碑负面信号 | 部分能（核对与更正是用户能做的；风险记录本身不能"消除"） | 事实状态 + 核对卡，**不打努力分** |
| **采纳** | AI 会不会"推荐"你 | 最近一次合格实测（是否被提及、被推荐、是否挂上自有信源） | 能（内容与分发是间接干预） | 证据 + 引导实测/补测卡 |

### 3.1 内部还有更细的维度，但只定性描述

每一层内部都拆成了若干可判定子项，并有全国统一的判定口径（比如信源层会分别看官网可达性、AI 爬虫是否被放行、页面是否可摘录、关键决策信息是否齐全；信任层会做主体一致性与风险记录核对；采纳层会看提及、推荐与挂源）。

这些细项我不在公开文档里展开，原因有两个：**一是对读者没有价值**——面试官关心的是"你怎么把模糊说法变成可判定项"，而不是具体阈值；**二是**这些口径是产品的核心资产，写细了等于公开评分规则。

### 3.2 还有一层"关联"，但它不参与归因

内部还有第四层：**关联（场景覆盖）**——用一份冻结的场景框架去审计"买家的关键场景有没有被问法覆盖"，没覆盖的场景提示补测。它是**覆盖审计**，不是归因：所以它不出现在三层归因里，也不进雷达投票，只以"未覆盖场景清单 + 补测卡"的形式出现。

这个拆分是我刻意的：**归因要收敛，审计可以发散**。如果什么都往归因里塞，最后用户看到的又是一堆"你很差"的结论。

## 4. 六个设计约束（规格里定死的部分）

| # | 约束 | 为什么 |
|---|---|---|
| D1 | 维度分四层（信源 / 关联 / 信任 / 采纳），旧的"推荐/口碑/触达"只作为实测问法分类 | 问法分类不是诊断维度，混用会让用户以为"多问几次口碑题就能提高诊断分" |
| D2 | 数据来源三分：官网自查 / 合格实测 / 全网信源清单 | 每个结论都能说清"从哪来"，避免模型猜 |
| D3 | 形态：四层客观结论 + ≤5 张行动卡；**不做 0–100 黑盒总分、不把提及率搬上诊断页** | 分数解释不了原因，行动卡才能指导下一步 |
| D4 | 信任层是**主体事实核对**，不是"AI 信任分" | "信任"是事实与风险状态，不该被打成"努力得分" |
| D5 | 可追溯，但**不做显式版本号**：结果快照只引用实测 id、问法原文、回答原文 | 版本管理是昂贵的工程；引用来源足够回答"当时基于什么" |
| D6 | 雷达只让"可干预供给项"投票；结果项、未测项、无问题项一律不制造通过 | 见 §2 条件一与条件三 |

### 补充：什么叫"合格实测"

诊断读的实测必须是合格的：状态完成、覆盖当前已配置的全部平台、问法集是当前题集、并且每类问法达到下限（推荐题、口碑题、触达题各有最低数量）。

但注意：**合格门槛只是"能不能读这份结果"的开关，不是"结果层可以打通过"的开关。** 这两件事我在规格里分开写，因为混在一起就会出现"因为数据完整，所以结论都通过"的逻辑。

## 5. 雷达图：把"未核查"画成"待解锁"

雷达是诊断页的门面，也是最容易骗人的地方。

- 外框与半框正常画；**内多边形只连接有值的维度**；
- 没有可投票项的层（关联 / 信任 / 无官网时的信源与采纳）**不形成顶点，相邻边断开**，从中心沿该轴画灰色虚线 + 空心问号，轴标签置灰，标注"待解锁"；
- 有值的层旁标"已核查 k / n"；
- 图例区分：实心 = 官网供给通过比例；灰色虚线 + ? = 尚未核查 / 进阶待解锁；
- **禁止用 0 兜底**把 null 画到中心。

> 一个产品细节：轴断开只表示"这层没有可投票的供给项"，不代表这层空白。该层的症状（如口碑负面）与证据仍然以行动卡和明细呈现——否则会出现"轴是空的，但下面全是问题卡"的视觉矛盾。

---

## 6. 行动卡：给"下一步"，不给"评分表"

诊断页的主角不是雷达，是**行动卡**。

- **固定序数优先级**：按问题类型固定名次（官网不可达 > 爬虫被拦 > 尚无合格实测 > 场景未覆盖 > 首页不可摘 > 决策信息不足 > 口碑负面 > 主体待核对 > 风险记录 > 爬虫待核对 > 全网信源为 0 > 实测过期），只生成"当前存在"的卡，**高名次在前，取满 5 张即停**；
- **不搞加权连乘**：早期我设计过"影响 × 置信度 / 难度"的连乘排序，后来删了——乘出来的分数无法解释，用户会质疑"凭什么是这张第一"。固定序数虽然简单，但可解释、可复现；
- **小样本只出"建议核对 / 补测"，不出率**；
- 每张卡可手动标"待办 / 已完成"，跨诊断保留；如果上次标了已完成、这次同类问题仍然存在，提示"该项仍未改善"；但本次**未评估**时不提示（不能把"没测"说成"没改善"）。

## 7. 合规如何反向决定架构

诊断要接第三方企业信息数据（工商、司法风险等）。数据源的协议约束直接改变了产品架构：

1. **数据不出境、不入库**：这类数据只能实时拉取、即时渲染，缓存放境内且不写进主库。于是"信任层"被做成独立实时模块，而不是诊断快照的一部分；
2. **公开展示需要书面授权**：把第三方数据展示给注册用户，属于协议里的"公开展示/提供给第三方"，需要书面授权。**授权未签，这个模块就不上线**——这是硬门，不是"以后补"；
3. **页面上必须给官方来源链接与采集时间**，声明"以官方登记/官方渠道信息为准"；诉讼类信息给证据与法律途径，**不给"消除入口"**；
4. **不采集 AI 平台账号**：诊断不调网页采集，所以不占采集账号、不需要验证码，也不与实测互斥（单次诊断约 1–3 分钟）。

> 这段是我最想在面试里讲的部分之一：**合规不是上线前法务补的 checklist，它会直接决定模块边界与数据流。** 如果一开始把第三方数据写进主库，后面改起来就是重构。

## 8. 实现与验收状态（诚实）

这套模型有完整规格与发布前验收清单，但项目在 2026.10 中止，实际状态是：

- **已实现**：四层维度与五态判定、结果层读合格实测、官网类根因自查、雷达（含 null 断开与 k/n）、≤5 张行动卡与手动状态、行动卡固定序数；
- **未接入**：第三方企业信息数据源（授权未签，信任层大部分维度只能是"未评估"）、全网信源清单适配器（已写好但未接入）、场景覆盖审计（关联层）；
- **未走完**：发布前验收清单（雷达 null 处理、robots 双轨 UA、证据下钻、并发与超时兜底等逐项核对）没有完整跑完；
- **受限**：没有合格实测的新用户，诊断只能出官网类根因与"先去做第一次实测"的卡。

**已知的坑**（都已记录在设计里，部分已修）：

- 把"未核查"画成 0 分（已定为 P0 级问题，修复方向是 null 断开 + 待核查标注）；
- 爬虫规则只看单一 UA 会制造虚假安全感，必须区分"训练通道"与"当期联网通道"，未确认的 UA 标"需核对"而不是"没拦=通过"；
- 行动卡如果没有固定序数，排序会变成"文档说一套、代码做一套"。

## 9. 复盘：诊断这件事我学到什么

1. **"可归因"比"全面"重要**：四层维度已经够多，真正让用户行动的是 ≤5 张卡。维度越多，用户越不知道该干嘛。
2. **反对一个行业惯例，要能说清"那我用什么替代"**：我反对 0–100 总分，替代品是"三层结论 + 行动卡 + 可追溯证据"；如果没有替代品，反对就只是姿态。
3. **合规约束要在设计阶段进模型**：第三方数据的"不落库、不出境、需授权"不是实现细节，它决定了信任层是不是快照的一部分。
4. **"未评估"是一种需要设计的状态**：它必须有视觉、有文案、有上游引导（去实测 / 补资料），否则用户会把它读成 0 分或通过。
