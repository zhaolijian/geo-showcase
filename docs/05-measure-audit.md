# 把"温度计"拆开：品牌实测指标的自审复盘

> 项目卡片 · 2026.10 · 角色：被审对象 + 报告作者 · 状态：自审报告已出，问题清单进入路线图；项目 2026.10 中止

这篇文章是一次**自我审查**的记录：我把自己设计的"品牌实测"模块当成外部产品来挑错。结论先说：**没有 P0，但有 10 个 P1、18 组 P2，且它们指向同一类方法论短板。**

对一个"可信度即全部价值"的模块，写这种报告比写功能清单有用得多。

---

## 1. 为什么要自审：温度计必须可信

品牌实测在整条闭环里的存在意义，是**可信地回答五个问题**：

1. 我的品牌在各 AI 引擎的答案里**到底可不可见**？
2. **被谁引用**（哪些信源 / 域名）？
3. **趋势如何**（变好 / 变差）？
4. **证据是什么、能否回溯**到当时 AI 的原话？
5. **下一步该改什么**？

如果数据不可信——探针不真实、样本有偏、口径混乱、证据不可回溯——那么模块做得再好看也没有价值。**它不是一个功能，它是整条闭环的度量地基。**

所以这次自审的最高标尺不是"代码有没有 bug"，而是：**用户能不能相信这个数字，并据此做决定？**

---

## 2. 方法：用真实数据流而不是功能清单去审

1. **先读设计文档再下结论**：通读规格、指标设计、实现计划、状态评审、路线图、探测可行性、延后项——先分清哪些是"有意为之的边界"，避免把已知取舍当新发现；
2. **按真实数据流走查**：从界面 → 接口 → 探测任务 → 浏览器采集 → 解析 → 落库 → 聚合 KPI → 证据/报告，逐环核对；
3. **四条并行专项**：探测链路、聚合与数据模型、UI/UX、竞品对照；每条发现都要求证据落地（真实数据、截图或可复核的代码位置）；
4. **独立复核**：对最关键的几条（样本量 n 未渲染、聚合层无测试、逐题状态缺失、面板失败静默跳过）做二次抽查，确认不是误判；
5. **三分类**：每条标注"**真缺陷 / 有意为之的红线 / 阶段取舍**"——已知的后置项不算新发现，红线不允许以违反的方式补齐。

---

## 3. 结论：P0 = 0，P1 = 10，P2 = 18（组）

**总评**：工程骨架与方法论自觉明显高于一般 MVP——

- 探针是真实本地浏览器 + 真人登录态（不是接口模拟冒充 C 端）、每题新会话、登录态本地留存不上云；
- 失败不污染率值；样本量 n 在数据层全程透出；趋势的"可比性"守得严；证据一次点击下钻到原文；
- 核心闭环（实测 → 看数 → 下钻 → 复测）真实可用，**无 P0**。

**但**以"温度计必须可信"对照，存在一类共同短板：

> **系统在"理想协议"下是正确的；当现场条件偏离理想协议时（记忆没关上、来源面板没打开、模型静默升级、引擎前端改版、探测中途切号），多处选择"静默继续 + 仍按理想协议落库"，而不是硬失败 / 打标 / 隔离 / 告警。**

这会**在无人知晓的情况下**让样本条件与标注口径不一致。对一个"可信度即全部价值"的模块，这是最需要补的洞。

另一个独立问题：**数据层已经算好的样本量 n，界面完全没有渲染**——小样本（比如 8 个答案）被四舍五入成醒目的精确百分比（"13%"），与"小样本不假精确"的自我要求直接矛盾。

---

## 4. 指标口径：数字是怎么来的

### 4.1 三类问法与三个核心指标

实测按用户真实会问的三类问题组织：

| 问法类型 | 用户处在什么阶段 | 看什么 |
|---|---|---|
| **推荐类**（某场景下有什么品牌/服务商推荐） | 选型 | 品牌是否被提及、是否进入推荐位 |
| **口碑类**（某品牌怎么样 / 有什么负面） | 验证 | 品牌信号是推荐、中性还是不推荐 |
| **触达类**（某品牌怎么联系 / 官网是哪个） | 行动 | 品牌信息是否被正确给出 |

核心指标：

- **提及率**：被提到的题数 / 有效题数；
- **推荐率**：进入推荐位的题数 / 推荐类有效题数；
- **自有信源引用率**：至少 1 条引用命中自有域名的回答数 / 全部合格回答数（分母是"全部合格回答"，不是"有引用的回答"，否则会系统性高估）。

### 4.2 几条我必须守住的规则

1. **失败不污染率值**：失败的题不进分子也不进分母；残缺的实测不进 KPI（避免幸存者偏差）；
2. **分母口径要写清**：分母是 0 时返回"无数据"而不是 0%，否则"0%"和"没测"不可分；
3. **趋势可比性**：换题集、换引擎、换协议版本之后，前后两期不可比，必须标"不可比"而不是画一条连续的线；
4. **五档信号不压缩**：推荐 / 备选 / 中性 / 不推荐 / 未提及，五档压成四档会让"主推"和"备选"不可区分；
5. **小样本不假精确**：结果数量低于 30 时，主数字用分数（1/8）或降精度（~13%），并**常驻**"样本小，仅供趋势参考"——不能只藏在 tooltip 里。

> 事实是：这些规则里有几条在自审时**没有做到**。规则写下来了，但没有进入 UI 的实现清单，就等于没写——这也是我后来在验收标准里加"每条指标必须有对应的界面证据"的原因。

---

## 5. P1 问题模式（挑 5 个有代表性的）

### 5.1 "静默继续" vs "fail-closed"：同一套系统两种口径

- **现象**：切换"快速模式"失败时会硬失败（中止探测、提示需要人工介入）；但关闭"记忆/历史"失败时只是静默返回，继续探测，落库时仍标注为"记忆关闭"。
- **为什么严重**：记忆是否关闭，决定了 AI 的回答有没有被用户的个性化历史污染。**在污染条件下采样、却标注为干净条件，比不测更糟**——数据是真的，但代表不了它声称代表的东西。
- **同一个洞的另一面**：答案的"来源面板"打不开时被静默跳过，引用列表记为空，该题被计为"未被引用"，而整次实测仍然算完成、正常进入分母 → **引用率系统性假阴性，且运维无感**。
- **修复方向**：能校验的开关一律 fail-closed（校验失败就硬失败或打标隔离）；证据采集失败必须落"采集失败"标记并告警，连续失败直接判"需要人工介入"，不进分母。

这条后来被我写进了自己的原则：**产品要替用户区分"没发生"和"没测到"，系统内部也一样。**

### 5.2 n 已算好，但界面上不存在

- **现象**：数据层已经在算样本量，接口也下发了，但界面组件里根本没用；"13%"实际是"8 次里 1 次"。
- **为什么严重**：这是"小样本不假精确"这条红线在 UI 层的失守。用户会把"8 次中 1 次"读成"13% 的份额"。
- **修复方向**：大数字下常驻小字 `n = 8（4 个推荐类问题 × 2 个平台）`；tooltip 也给出本次 n。

### 5.3 小样本精确整数 % 与醒目的 delta

- **现象**：百分比四舍五入到整数；单次变化的 delta 用 pp 表示且视觉上很醒目（"+13pp"看起来像趋势，实际只是多命中了一个答案）。
- **修复方向**：小样本降精度/用分数；"样本小"的提示常驻卡面，而不是 hover 才见；delta 的视觉权重低于绝对值。

### 5.4 单题失败、整个引擎的 N 题作废

- **现象**：一题遇到验证码/超时就抛错，整个引擎的本轮实测作废重跑，且逐题没有状态记录，事后查不到"是哪道题、为什么失败"。
- **判断**："残缺的实测不进 KPI"方向是对的（避免幸存者偏差），但代价是吞吐与成本受损、问题不可诊断。
- **修复方向**：保留"残缺不进 KPI"原则，同时在实测与逐题记录上补失败原因与状态，给单题重试预算，为逐题容错铺路。

### 5.5 协议快照不记模型版本：趋势混入模型漂移

- **现象**：快照记录了模式、域名、品牌名，但没有记录"当时页面上的模型版本"；模型静默升级后，跨期数据不可比，而看不出来。
- **为什么严重**：趋势是这个模块的主用途；如果趋势里混入了模型版本变化，用户会把它当成自己的优化效果。
- **修复方向**：快照补"检测到的模型版本"，三个引擎的采集口径对齐。

另外还有一类**工程但直接影响可信度**的问题：聚合层（把逐题结果拼成 KPI 的装配逻辑）没有单测。纯函数算得对，不代表拼出来的 KPI 对；跨引擎合并、Δ 可比性、品牌过滤都在这层。

## 6. 能力缺口 ≠ 缺陷（而且要分清红线）

自审里我特意把"还没建的能力"单独列出来，避免把路线图当成 bug 清单：

| 能力缺口 | 说明 | 建议时机 |
|---|---|---|
| 引擎覆盖 | 当时只覆盖 3 个国内平台，竞品普遍 5–12 个 | P1→P2 |
| claim 级事实核查 | 只做到"引用来源"，没到"这句话有没有依据" | P2–P3 |
| 竞品 SoV / 相对位置 | 只能跟自己比，没有品类基准 | P3 |
| 行业基准 | 没有"你在品类里排第几" | P2–P3 |
| 原生告警 / 定时监测 | 全手动触发 | P2 |
| 报告导出 / 可分享快照 | 无法发给老板/客户 | P2 |
| 分引擎信源偏好榜 | 只有引用下钻，没有"品类靠哪些域名" | P2 |
| 品牌 vs 信源双指标 | 五档只覆盖"被点名"，没覆盖"被引用但没被提到" | P2 |
| 触达质量打分 | 有触达问法但没有对错判定 | P2 |
| 多品牌 / 多门店 | 一用户一品牌，代运营刚需 | P3（影响数据模型，宜预留） |

**红线（不作为缺陷、也不建议违反）**：不承诺必被引用；不自动发布/不养号；**不云端托管用户平台 Cookie / 账号密码**；不做短态平台流水线；桌面优先。

> 这个区分很重要：能力缺口是"还没做"，红线是"做了就错"。混在一起，做产品的人很容易用"补齐能力"的名义去碰红线。

---

## 7. 竞品对照：我看到了什么，以及我选择不做什么

当时对照了 20 多家公开产品的功能与定位（只看公开资料，不推测内部实现），可以把它们归成两类：

- **竞品 A（国际类商业 GEO SaaS）**：指标体系成熟（可见性、引用、情感、竞品对照、事实核查），频率高、报告强；但它们**普遍不覆盖国内中文 C 端平台**，对国内中小企业不可直接使用；
- **竞品 B（国内类商业 GEO SaaS）**：覆盖国内平台，功能从监测到写稿到分发一条龙；但多数仍以"合成指数 / 总分 / 曝光"作为主指标，黑盒程度高。

三个判断：

1. **国内中文 C 端是国际产品的系统性空白**。这个产品能做"真人本地探针 + 不云端托管账号"，这既是合规选择，也是差异化；
2. **claim 级事实核查是行业军备竞赛**。我当时只做到引用层，这是最明确的能力差距，但我选择后置——因为它需要人工金标与一致性校准，成本远超 MVP 阶段能承担的量；
3. **这个产品真正的空档不在功能多少，而在"可信度设计"**：触达类问法的对错判定、三类问法的自动分桶、证据一次点击下钻、不做黑盒总分——这些是"让数字可信"的功夫，比多接几个引擎更难被抄。

---

## 8. 路线图：先补可信度，再扩能力

排序原则：**可信度收益 × 成本**，quick win 优先；先补"静默不一致"的 fail-closed 与 n 展示，再做结构重构与能力扩展。

| 梯队 | 做什么 | 为什么在这 |
|---|---|---|
| **第一梯队（1–2 周）** | 顶栏数字标 n；小样本改分数/降精度；关记忆 fail-closed；协议快照补模型版本；主推/备选区分；趋势图固定基线、null 点画占位；分母 0 返回"无数据" | 成本小、直接修复"误导"；数据大多已在手 |
| **第二梯队（2–4 周）** | 来源面板失败打标 + 告警 + 连续失败转人工；逐题状态与失败原因；切号逐题记账号；聚合层装配测试；引擎改版真机冒烟；可访问性 | 修的是"静默污染"与"不可诊断"，成本中等 |
| **第三梯队（按信号）** | 报告导出、原生告警、信源偏好榜、双指标、触达打分、引擎扩展、claim 级核查、竞品 SoV、多品牌 | 需要商业化信号或数据规模支撑，避免提前投入 |

> 如果这个项目继续，我会先做完第一梯队再谈任何新功能——因为**用户不会因为功能少而离开，会因为数字不可信而离开**。

---

## 9. 局限（这份自审本身也不完美）

- 实证基于**本地开发环境的真实数据**，账号与品牌已匿名；不代表生产环境与商业效果；
- 部分状态（探测进行中、风控触发、部分引擎失败的活态）**只做了静态审查**，没有真机触发；
- 竞品的精度与规模是官方自报，**没有独立实测**，已与第三方来源区分；
- 样本小：自审结论对"这个模块"成立，不能外推成"整个 GEO 行业都这样"；
- 报告写完时项目即将进入阶段性中止，第一梯队的一部分修复没有落地——**这是"知道问题但没时间修"的典型状态**，也是我把它写下来的原因。

---

## 10. 复盘

1. **自审要用"外部人视角"**：如果我按功能清单自检，结论会是"都做了"；按第一性原理问"用户敢不敢信这个数"，才发现一堆静默问题。
2. **"静默"是最贵的 bug**：报错会被人看见、被修；静默污染会在几个月后变成"这个产品数据不准"的口碑，且找不到原因。
3. **不假精确是一种产品能力**：它要求数据层、接口、UI、文案一起改；只改文案等于没改。
4. **分清"没做"和"做错"**：能力缺口可以排期，红线不能碰，缺陷必须修——三类混在一起，优先级一定乱。
