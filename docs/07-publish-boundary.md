# 分发边界：为什么只同步到草稿箱，不代发布、不养号

> 项目卡片 · 2026.07 定案 · 2026.10 补充"免安装"方案调研 · 角色：产品定义 + 同步链路设计 · 状态：草稿箱同步已上线，依赖用户侧浏览器扩展

"发布"是这类产品最诱人的一环：能一键发布到全平台，演示效果最好、最容易卖。我选择只做到草稿箱——这不是技术做不到，而是**产品判断：发布权不能放在 SaaS 手里。**

---

## 1. 问题：最后一步是价值最大的一步，也是最危险的一步

内容产品的链路是：诊断 → 选题 → 生成 → 编辑 → **分发** → 回测。

对用户来说，"分发"是价值兑现的临门一脚。但这一步同时踩在三条红线上：

1. **平台规则**：多数平台禁止或限制自动化发布；自动终发属于灰区，账号被封的代价由用户承担；
2. **账号安全**：要代发布，就必须拿到用户的平台登录态（Cookie / 密码 / 扫码会话）；云端一旦持有这些凭证，泄露风险与责任都无法兜底；
3. **信任**：如果产品承诺"自动发布"，它实际上承诺了"保证过审、保证不被限流、保证有效果"——这些都不是我能控制的。

---

## 2. 决策：MVP 的"发布" = 同步到平台草稿箱 + 人工终发

**产品定义锁定**：

> 源引不发任何一篇文章。它把成稿同步到用户已登录的各平台**后台草稿箱**，回传草稿链接与状态；**审核、终发、发布节奏由用户在平台后台决定。**

### 2.1 背景 → 取舍 → 结论 → 代价

- **背景**：如果做"直接发布"，产品看起来最完整，也能收更高的价；但三条红线都会破。
- **取舍**：自动化程度（体验、卖点）vs 合规与账号安全（长期信任）。
- **结论**：只做草稿箱；登录态不出用户浏览器；执行由用户侧扩展完成，SaaS 只做内容中台与状态回传。
- **代价**：
  - 体验不闭环——用户还要去平台点"发布"；
  - 需要用户**额外安装浏览器扩展**、逐个平台登录，安装漏斗天然有流失；
  - "同步成功率"受平台前端改版影响，产品必须长期背着适配维护税；
  - 无法承诺"发布成功"，只能承诺"草稿已创建"。

我接受这些代价，因为**一个 SaaS 拿不到用户的平台凭证，也就没有能力做坏事**——这既是安全边界，也是我能对用户说的最硬的一句话。

---

## 3. 怎么落地：SaaS 做内容中台，执行在用户侧

### 3.1 架构分工

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| **SaaS（内容中台）** | 文章内容、平台选择意图、同步状态记录、深链、同步前合规扫描 | 不接触平台凭证、不直接调平台写接口、不自动终发 |
| **用户侧执行器（浏览器扩展）** | 用用户本机的登录态，逐平台打开创作者后台，把正文写入草稿，回传结果 | 不上传 Cookie、不保存密码、不做风控绕过 |
| **平台** | 草稿箱、审核、发布 | — |

**通信原则**：只传标题 / 正文 / 平台元数据；回传成功/失败/待确认、草稿链接、错误原因；**Cookie 永不进服务端**。

### 3.2 平台排序：给建议，不给"推荐"标签

同步列表的顺序按"内容形态匹配 × 实现容易度"做启发式排序（**这不是效果承诺**）：

1. 知乎、公众号、CSDN、掘金等长文/可摘录载体靠前；
2. 已登录的平台优先展示；
3. B站专栏、简书、头条、百家号、网易号、搜狐号等居中；
4. **小红书 / 抖音在列表沉底**，并附一行形态说明（长文 Markdown 与短态平台形态错位）；
5. 不锁死平台、不自动勾选——用户自己决定同步到哪。

我刻意**没有做"按篇幅推荐平台"的角标**：篇幅匹配不等于 GEO 可见度，"推荐"两个字会被读成流量或 AI 曝光承诺。

### 3.3 三级跳转：让用户永远能"接着往下走"

| 优先级 | 行为 |
|---|---|
| 1 | 有精确草稿编辑页 → 新开该页 |
| 2 | 只有草稿箱列表页 → 打开列表，提示按标题查找 |
| 3 | 同步失败 → 复制正文（Markdown/HTML）+ 打开平台"新建文章"页 |

尤其是公众号：插件路径返回的编辑链接常带临时 token、会过期；官方接口通常只有 media_id、没有稳定单篇深链——所以**必须准备列表页兜底**，不能假设深链永远有效。

### 3.4 失败必须可解释

同步结果有三种终态：草稿已创建 / 失败 / 待确认；另有"当前平台不支持"这类前置状态。失败原因分平台、分类型（未登录、扩展未安装、平台改版、内容超限……），并且**不允许出现"无原因失败"**——用户不知道错在哪，下次就不会再试。

同步前还有一道**合规扫描**：正文里的手机号、微信号、导流短语等会被提示——不是为了阻止用户发，而是避免用户在平台侧踩审核雷。

### 3.5 同步就绪的硬性检查

同步前只挡会导致"错误交付"的技术条件：稿件未保存/保存失败、正文为空、稿件版本冲突、平台或扩展不可用、正文图片无法加载。质量报告不是发布审批（见 [02](./02-article-agent-prd.md) §6.2）。

---

## 4. 明确不做（红线）

| 不做 | 理由 |
|---|---|
| **不做自动终发 / 定时群发** | 平台规则灰区 + 用户账号风险；终发是用户的决定 |
| **不做云端托管 Cookie / 账号密码** | 安全红线：平台凭证一旦上云，泄露与责任无法兜底 |
| **不做"矩阵养号"** | 与产品价值无关，且是平台明确打击的行为 |
| **不做 Electron 客户端（MVP）** | 包体大、签名/公证成本高、平台适配维护重；先把"草稿+跳转"验证掉 |
| **不一次铺齐十几个平台** | 适配维护税会吃掉所有精力；先做 3 个高价值平台（长文/可摘录），验证需求再说 |
| **不承诺"发布成功 / 过审 / 不被限流"** | 这些不归产品控制；承诺等于制造期望债 |

---

## 5. 后来发现的问题：期望差本身就是产品债

2026.10 我做了一次全局批判性评审，其中一条自我批评很扎心：

> 产品对外说"一键同步"，但用户实际要先**安装浏览器扩展**、**逐个平台登录**，才能用。

这不是文案问题，是**期望管理失败**：用户点"同步"之前不知道有这个门槛，点完才发现——流失就发生在这里。

于是我做了一轮"免安装同步"的专项调研，把行业路径全谱摸了一遍，结论是：

| 路径 | 是否免安装 | 是否碰用户账号 | 判断 |
|---|---|---|---|
| 官方开放接口 | 是 | 不碰 | 只覆盖极少数平台（当时核到 2/14 左右），且需要企业资质与权限确认 → 不可作为主路径 |
| 云端 RPA / 代发聚合 | 是 | **要托管账号/Cookie** | 与红线根本冲突，**明确拒绝** |
| 本地桌面应用内自动化 | 免扩展但需装桌面应用 | 不碰（本地登录态） | 可行但成本高（签名公证、包体、平台适配），置"触发档" |
| 小书签 Bookmarklet | 是（零安装） | 不碰 | 半自动、性价比高，但要逐平台实测 CSP 与后台兼容性 |
| **富文本一键复制 + 发文页深链** | 是 | 不碰 | **最稳、零风险**：多一次人工粘贴，但完全不碰账号凭证；建议作为默认降级路径 |
| 国外 OAuth 聚合服务 | 是 | OAuth 授权 | 一个国内平台都不覆盖，不可用 |

最终建议是：**把"复制即走"做成默认路径**（零安装、零风险、人在环中），浏览器扩展作为增强能力（装了更顺、没装也能用）。这个方案当时评估约 6.5–8 人天，是"免安装"诉求下最快、最稳的落法。

**这件事的教训**：技术捷径（依赖第三方扩展）能让你更快上线，但**它会以期望差的形式变成产品债**，最后仍要还。如果重来，我会第一版就同时提供"复制即走"的降级路径。

---

## 6. 边界与代价（诚实）

- **同步成功率不可承诺**：平台前端改版、登录过期、扩展未安装都会导致失败；产品只能保证"失败可解释 + 可降级"；
- **依赖第三方执行器**：扩展能力与平台适配由第三方维护，我只维护平台注册表与 HTML 适配；这既是省成本，也是**依赖风险**；
- **多平台 ≠ 有效分发**：同步只是把内容放到了平台，阅读量、审核、推荐都不由产品决定；我在产品里也明确不把"阅读数"当 GEO 效果指标（见 [05](./05-measure-audit.md)）；
- **适配维护税长期存在**：每接一个平台就多一份选择器/格式适配的维护；
- **期望管理要写在第一屏**：安装门槛、需登录、终发在平台，这三件事必须提前说清，不能等用户点进同步页才发现。

---

## 7. 复盘

1. **红线要写进产品定义，不是写在合规文档里**："不托管 Cookie、不自动终发"被我写进了 MVP 的产品定义与验收标准；它不是上线前补的说法，而是决定架构的约束。
2. **"自动化"不是越彻底越好**：分发这件事，产品真正的价值是把内容准备到"离发布只差一步"，而不是替用户按下发布键。
3. **技术捷径会以期望差的形式回来**：依赖第三方扩展很快，但"要不要让用户装扩展"是产品决策，不是实现细节。
4. **失败处理是这类功能的主体**：同步功能的体验，90% 体现在失败时用户知不知道发生了什么、下一步能干什么。
